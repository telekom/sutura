# Entropy catalog

Status: **accepted**, 2026-11-02 (issue #1729). These are the owner's decisions. Built so far: the
configuration (`catalog.kind: entropy`, its sign-in and its bindings) and the client credentials
grant it signs in with. **No build links the reader**, so every build refuses the kind by name at
boot.

## The question

An Entropy Data deployment holds data products whose output ports each name a data contract and a
server. sutura reads them as a catalog. Four things were open:

1. A contract's metric `formula` is free text, which nothing can compile. Where does a certified
   metric come from?
2. May an `entropy` catalog sit beside a catalog of another kind?
3. A port and its contract can each name a server. Which one is read?
4. Which specification versions are read?

## Decision

1. **Metrics come from a declared `metric_property`** in the contract's `customProperties`, as a
   `datahub` catalog's do. The parser that reads the property moves to a place both readers share.
2. **One catalog kind per deployment.** `open_catalog`'s refusal of mixed kinds stays.
3. **A port's server is read only when the port and the contract agree on it, or when only one of
   them names it.** A conflict is a typed load refusal naming the product and the port. A port's
   server has no `type` and free keys, so servers are compared by the type-specific keys below.
4. **ODCS v3.x and ODPS v1 are read.** The older DCS and DPS shapes are refused by name.

## Sign-in

A deployment declares exactly one mode. Both are the deployment's identity reading metadata: **no
caller's identity reaches the marketplace.** What a caller may read from a data system is decided by
that source's own posture, not by the catalog.

| Mode           | Sent as                                                                                                            | Reads                                                                                      |
| -------------- | ------------------------------------------------------------------------------------------------------------------ | ------------------------------------------------------------------------------------------ |
| `api_key_file` | `x-api-key`                                                                                                        | whatever the key's owner - an organization, a team or a user - can see                     |
| `oidc`         | a bearer token from the client credentials grant at `token_endpoint`; `client_auth` is `basic` (default) or `post` | an agent client reads only the endpoints open to agents, products and contracts among them |

What `oidc` does not cover:

- **An external issuer's `aud` is checked only when the marketplace registers that issuer with an
  audience.** sutura cannot see that registration, so it cannot refuse a deployment that lacks one.
- **The REST scope is undocumented.** The authorization server advertises only `mcp`, `mcp:read` and
  `mcp:write`. `scope` is sent as written and omitted when absent.
- **An issuer that needs an `audience` or `resource` parameter** is not served; only `scope` is
  sent.
- **The token endpoint and `scope` load unchecked.** The crate that sends them parses them, and no
  build links it yet.

## Bindings

A contract's server names its system by `type`. A deployment binds each server it serves to a
declared source:

| `type`                   | Identified by                                                 |
| ------------------------ | ------------------------------------------------------------- |
| `bigquery`               | `project`, `dataset`                                          |
| `postgres`, `postgresql` | `host`, `port`, `database`, `schema`                          |
| `clickhouse`             | `host`, `port`, `database`                                    |
| `oracle`                 | `host`, `port`, `service_name` (the contract's `serviceName`) |
| `duckdb`                 | `database`, optional `schema`                                 |

`cloudsql` is not bindable: no source kind dials it. A binding's source must be declared and of the
type's kind, and a key the type does not read is refused. Two bindings of one server are refused.

**Only Postgres is compared with its source**: the binding's `database` must be the one the source
dials. A host or a service name has more than one spelling, so a binding to the wrong host of the
right kind loads.
