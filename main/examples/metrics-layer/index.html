    Metrics layer¶

    This example runs sutura for several users with Cube as the only data system. Keycloak is the identity provider. DataHub is the catalog, read with one token for every caller. Cube computes each metric, and Cube decides which rows each caller reads.

    The example is in examples/metrics-layer:

    Path Contents
    conf/impersonation-at-source.yaml The sutura settings: Cube receives each caller's own token
    conf/shared-service-user.yaml The sutura settings: Cube receives the deployment's token
    keycloak/realm.json The realm with the callers alice and bob, and four clients
    cube/model.yml The Cube data model, with an access policy on orders
    clickhouse/init.sql The tables that Cube reads
    compose.yaml A live DataHub, and the loader that writes the catalog into it
    compose.cube.yaml Keycloak, ClickHouse, Cube and the TLS proxy in front of Cube
    loader/load.py The catalog that the loader writes into DataHub
    setup.sh Writes the secrets to .env, and the CA of the TLS proxy

    All data is synthetic.

    The parts¶

    compose.cube.yaml runs the three services of this example by hand (see Run the services): keycloak imports keycloak/realm.json, clickhouse loads clickhouse/init.sql, and cube serves cube/model.yml over clickhouse, verifies each token with the keys of the realm, and accepts only the issuer of the realm and the audience cube (cube-tls is the TLS proxy in front of it). just dev-up-cube starts the same three as cube-keycloak, cube-clickhouse and cube-metrics in the cube profile of compose.services.yaml, for the tests of this repository.

    The DataHub catalog holds the orders and customers datasets and the certified metric revenue. Each dataset is a cube with the same name, and revenue is a measure of orders.

    Who reads what¶

    Each caller exists in Keycloak, in one group:

    Caller Group Revenue in June 2026
    alice north 262345
    bob south 150000
    the sutura-deployment client north, south 412345

    The client scope cube writes these groups into the claim regions. The access policy in cube/model.yml gives each token only the rows of orders whose region is in its own regions claim.

    impersonation-at-source¶

    A caller signs in at the sutura client and sends the access token to sutura. sutura verifies it, then exchanges it at Keycloak as the client https://sutura.example.com for a token with the audience cube. Cube receives the caller's own token, so alice reads 262345 and bob reads 150000.

    The delegation of the source declares the exchange:

    sources:
  warehouse:
    kind: "cube"
    endpoint: "https://cube.example.com"
    token_file: "/run/sutura/cube-token"
    posture: "impersonation-at-source"
    verification_identity: "sutura-deployment"
    delegation:
      - token_endpoint: "http://127.0.0.1:8180/realms/metrics-layer/protocol/openid-connect/token"
        client_id: "https://sutura.example.com"
        client_secret_file: "/run/sutura/exchange-secret"
        audience: "cube"

    Cube serves plain HTTP, and sutura sends a caller's token only over https. compose.cube.yaml puts a TLS proxy in front of Cube, and security.outbound.transport_anchors names its CA.

    token_file holds a token of the sutura-deployment client. sutura sends it only for the checks it runs at startup. verification_identity names the identity of those checks, because the revenue metric has an anchor.

    shared-service-user¶

    sutura sends the token of the sutura-deployment client on every request. Every caller reads 412345, the answer of the deployment. acknowledged_because on the source records why every caller reads as one identity.

    Run the services¶

    compose.yaml in the example runs DataHub on 127.0.0.1:8081, the catalog endpoint in both settings files, and its loader. compose.cube.yaml adds Keycloak on 127.0.0.1:8180, ClickHouse, Cube, and a TLS proxy for Cube on 127.0.0.1:443. From examples/metrics-layer:

    ./setup.sh
docker compose up -d --wait datahub keycloak cube-tls
docker compose run --rm loader

    setup.sh writes the secrets to .env, with COMPOSE_FILE so that docker compose reads both files, and the CA and certificate of the proxy. The certificates are valid for 30 days: delete .tls, run ./setup.sh again, run docker compose restart cube-tls, and start sutura again. The loader writes the orders and customers datasets, the relationship orders_to_customer and the metric revenue into DataHub. It also writes the files that sutura reads from /run/sutura to .local: the DataHub token datahub-token (the catalog token_file in both settings files), jwks.json with the keys of the realm, exchange-secret, and cube-token, a token of the sutura-deployment client. The realm issues tokens for an hour, so run the loader again when cube-token has expired. Then start sutura again: it reads the token at startup. Every port binds to 127.0.0.1 only.

    Run sutura¶

    sutura reads base.yaml in SUTURA_CONFIG_DIR, so a settings file under another name is not read. From examples/metrics-layer, give sutura the file you chose under that name and start it. The settings name Cube as cube.example.com, the host of the proxy certificate, and --add-host points that name at the proxy:

    export SUTURA_VERSION=0.9.0
mkdir -p .local/conf
cp conf/impersonation-at-source.yaml .local/conf/base.yaml
docker run --rm --network host --add-host cube.example.com:127.0.0.1 --user "$(id -u):$(id -g)" \
  -v "$PWD/.local:/run/sutura:ro" -e SUTURA_CONFIG_DIR=/run/sutura/conf \
  ghcr.io/telekom/sutura:$SUTURA_VERSION serve

    On Docker Desktop, turn on Settings > Resources > Network > Enable host networking first; with it off, 127.0.0.1:8080 does not answer. See Single player.

    Ask the example question as alice. $TOKEN is her access token from the sutura client of the realm (password grant, user and password alice), and the answer is 262345. As bob it is 150000:

    TOKEN=$(curl -s http://127.0.0.1:8180/realms/metrics-layer/protocol/openid-connect/token \
  -d grant_type=password -d client_id=sutura -d username=alice -d password=alice \
  | sed -n 's/.*"access_token":"\([^"]*\)".*/\1/p')
curl -s -X POST http://127.0.0.1:8080/v1/query \
  -H "authorization: Bearer $TOKEN" \
  -H 'content-type: application/json' \
  -d '{"metrics":["revenue"],"grain":"month","range":{"start":"2026-06-01","end":"2026-07-01"}}'
