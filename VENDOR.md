documentation, guidance, fixtures - which no dependency check can see.

### Distributed worker completion

The distributed engine also carries an opt-in completion request on its existing coordinator
channel. One terminal task message carries bounded opaque receipts; the query-owned channel task
checks identity, duplication, missing completion and aggregate bounds before successful EOF. The
head stream is dropped before cancellation and draining; the original non-opt-in shutdown order
is retained. The worker hook receives the actual final plan, or the base plan when no task ran,
and must finalize every started native read before returning. Its bounds are a capture-operation
limit, not a caller deadline, and receipts disclose execution rather than attest a peer.

The schema change belongs to the pinned upstream `codegen` generator; generated Rust must come
from it, never a hand-written delta. Its generator manifest is not transitively locked by the
upstream root lockfile, so regeneration must retain the resolved codegen lock and tool versions.
The vendored crate is excluded from workspace tests: its native-workspace consumer checks do not
run its private completion-state and metrics-receiver-drop cells. Those require an explicit
vendor test run. No new upstream publication accompanies this patch. Drop this hook when a
released upstream provides the same bounded terminal lifecycle and first-party consumers adopt it.

### Keeping this current, and who notices

Nothing notices automatically, and it is better to say so than to imply a process. `libmimalloc-sys`
pins its own bundled mimalloc, so neither `cargo update` nor a dependency bot can see the C at
all, and no gate compares `mimallocVersion` in `flake.nix` against upstream's newest tag.

So the mechanism is a person watching `github.com/microsoft/mimalloc/releases`. When a new mimalloc release
lands, three things have to happen together: bump `mimallocVersion` and `sha256` in `nix/mimalloc.nix`,
re-copy the subset into `c_src/mimalloc/v3`, and re-run the four-target proof.

**The drift hazard that follows from the fallback**, named because it is not obvious: the version
lives in TWO places. `nix/mimalloc.nix` fetches 3.6.1 for the cached archive, and `c_src` holds
3.6.1 for the bare-`cargo` path. They agree today. If a future bump changes one and not the other,
`nix build` and `cargo build` will link different allocator versions with no error, and the only
symptom would be `MIMALLOC_VERBOSE=1` printing different versions between the two.

The same hazard extends to compile-time posture, not only version: `nix/mimalloc.nix`'s comment
next to its `-D` flag list is the mechanism note for `MI_GUARDED` (guard-page heap-overflow
sampling) - compiled in, dormant by default, armed only by `MIMALLOC_GUARDED_SAMPLE_RATE` at
runtime - and it must stay identical in both paths or they disagree on allocator security
behaviour, not only on version. `MI_PADDING_CHECK_BYTES` (byte-precise overflow detection on
free, restored under `MI_SECURE=4` since 3.5.0) was this hazard's first realised instance: it
was on `nix/mimalloc.nix`'s side only until it was found and added to `build.rs`. Nothing
mechanical stops a third define from doing the same - see issue #858's own proposal for a gate
comparing the two define sets, not built here.

## ADBC BigQuery driver (telekom/sutura#913)

The native ADBC BigQuery driver is the Foundry `adbc-drivers/bigquery` (Apache-2.0),
**self-built from source** rather than pulled as a CDN `.so` from `dbc install bigquery` -
a CDN binary has no aarch64-musl artifact and is not reproducible for this repository's
four release triples. It is pinned at the release tag `go/v1.14.1`
(repo rev `a25673b7`) as flake input `bigquery-adbc-src`; `just update` does not chase
`main` past that pin.

Seven source-level adaptations, recorded here so nothing is silent:

- **go.mod floor relax.** The driver's `go.mod` declares a go floor (`1.27.3`) above what
  nixpkgs' `go_1_27` provides. `nix/bigquery-adbc-drivers.nix` relaxes the floor
  to `go 1.27` and drops any `toolchain` directive at the source, so both the module-vendoring
  FOD and the build accept the pinned toolchain. `1.27.3` is a patch floor; the relax changes
  the directive, not dependencies.
- **Two options for a caller's own Google credential.** `nix/bigquery-adbc-caller-credentials.patch`
  adds the `bigquery.auth_type` value `access_token` with `bigquery.auth.access_token`, a bare OAuth
  2.0 access token the driver sends as it is and never refreshes, and `bigquery.impersonate.subject`,
  which the driver copies into `impersonate.CredentialsConfig.Subject` for domain-wide delegation.
  Unpatched, every arm that authenticates holds a long-lived secret or calls a token endpoint
  itself, and the impersonation config has no subject. An empty token is refused, a token is
  refused unless `bigquery.auth_type` selects it (every other arm would drop it silently), a token
  beside any impersonation option is refused (impersonation would swap it for the deployment's own
  credential), and a subject without a target principal is refused. The patch adds
  `token_options_test.go`, which the build's check phase runs on a host that can run its target.
  sutura sets the token for a `google_login` source and the subject for a `domain_delegation`
  source.
  Upstream issue:

- **A statement option for the query job's labels.** `nix/bigquery-adbc-job-labels.patch` adds
  `bigquery.query.labels`, a JSON object of string keys to string values that the driver copies
  into `QueryConfig.Labels`; an empty value clears them and anything that is not such an object,
  JSON `null` included, is refused as `InvalidArgument`. Unpatched, the driver lists labels as a todo and has no way to set
  them. The driver checks no label rule; `BigQuery` does. The patch adds `labels_test.go`, which
  the build's check phase runs on a host that can run its target. sutura sets it on every
  request-time job (`docs/integrations/data-systems/bigquery.md`). Upstream issue:
  [`adbc-drivers/bigquery#372`](https://github.com/adbc-drivers/bigquery/issues/372). Drop it when upstream ships a
  labels option.
- **A query can start with `jobs.query`.** `nix/bigquery-adbc-jobs-query.patch` adds the database
  option `bigquery.query.through_jobs_query`. Set to `true`, a statement run by `ExecuteQuery` or
  `ExecuteUpdate` starts with `jobs.query` instead of `jobs.insert` (`ExecuteSchema`'s dry run and
  the session and transaction statements still use `jobs.insert`; sutura calls neither); the
  driver then follows the job it names with `jobs.get` and reads the
  rows through the Storage Read API as before. A `bigquery.readonly` token can make those calls and
  not `jobs.insert` or `jobs.cancel` - measured on 2026-10-22 with a service account's own token,
  not a domain-wide-delegation token, so the delegated principal type is not measured. The request
  is rendered by the client library's own `jobs.insert` encoder, on a client with no credential
  whose transport sends nothing, so parameters, `maximumBytesBilled` and `jobTimeoutMs` encode as
  they did; a rendered field outside the set `jobs.query` takes under the same name is refused
  with `NotImplemented`, never dropped. A dry run is a `jobs.query` dry run. Unpatched, a
  `bigquery.readonly` token can run no query at all. Limits: `jobs.query` takes no client-chosen
  job id, so a job cut off before `jobs.query` answers cannot be cancelled, and with the read-only
  scope no job can be (the driver logs the failed cancel); `jobs.query` is sent once, without the
  client library's retry. The patch adds `jobs_query_test.go`, which the build's check phase runs
  on a host that can run its target, and `jobs_query_labels_test.go`, which holds that the job's
  labels reach `jobs.query` exactly. sutura sets the option only for a `domain_delegation` source,
  beside the read-only scope. Its tests also need the caller-credentials patch's access-token
  option, and `jobs_query_labels_test.go` needs the job-labels patch's `OptionQueryLabels`, so it
  compiles only with that patch applied too. Upstream issue: [`adbc-drivers/bigquery#373`](https://github.com/adbc-drivers/bigquery/issues/373). `go/v1.14.1` starts a query
  with `jobs.query` itself under `bigquery.query.job_creation_mode=optional`, through the client
  library's `Query.TryRead`. That does not replace this patch: the pinned client library's
  fast-path probe declines any configuration with a job timeout, which sutura sets whenever a
  request carries a port deadline, and a dry run never takes that path. Drop it when upstream's
  `jobs.query` path carries a job timeout and a dry run and refuses a configuration it cannot
  carry.
- **Read a query's result as several partitions.** `nix/bigquery-adbc-partitions.patch` implements
  `(*statement).ExecutePartitions` and `(*connection).ReadPartition`, both unconditionally
  `NotImplemented` upstream. `ExecutePartitions` runs the query to a destination table exactly as
  `ExecuteQuery` does, then reads that table's own metadata once for its exact row count (`NumRows`,
  not the read session's `GetEstimatedRowCount`, which is an estimate) and returns it as
  `rows_affected` (a checked conversion; anything unrepresentable in an `int64` stays `-1`), then
  opens a multi-stream Storage Read API session (`CreateReadSession`) against that table and returns
  one partition descriptor per stream, with the result schema taken from the read session. A
  descriptor carries only the Storage Read API stream name (plus a version byte) - never a
  credential, token, or anything else identity-bearing - so `ReadPartition` can decode it and open
  `ReadRows` on that stream with whichever connection calls it, using that connection's own
  credentials, not the credentials of the connection `ExecutePartitions` ran on. That read sends
  no per-request serialization options - `BigQuery` refuses them on a session stream with
  `InvalidArgument` ("only supported for job streams"), measured at the venue - so the session
  carries the ZSTD buffer compression the job's default-stream read asks per request. A malformed
  descriptor is refused as `InvalidArgument`, never a panic. `ExecutePartitions` refuses a
  `bigquery.query.dry_run` statement outright (a dry run has no destination table to partition)
  rather than returning a partition list or substituting a row-count estimate, and refuses a
  statement with bound parameters as `NotImplemented` rather than running it with them ignored.
  `ReadPartition` cancels the stream's context when opening or decoding it fails, so no gRPC stream
  stays open behind an error that returns no reader to release.
  **Two statement options decide `CreateReadSession`'s `MaxStreamCount`:**
  `bigquery.query.partitions.max_streams` (a positive integer bounding how many streams are ever
  asked for; unset keeps `partitionStreamCount`, 4, today's fixed value) and
  `bigquery.query.partitions.target_rows_per_stream` (a positive integer; set, the exact row count
  is divided into stream-sized chunks, rounded up and capped at `max_streams`; unset keeps today's
  behaviour of always asking for `max_streams`). `partitionStreamCountFor` is the pure split
  function; neither option is clamped silently - zero, negative or non-integer is refused at
  `SetOption` with `InvalidArgument`. The session asks for that count as both its
  `MaxStreamCount` and its `PreferredMinStreamCount`, since a ceiling alone lets the server answer
  one stream for a small table. **Limit: streams asked for are not streams returned** - the
  preferred minimum is best effort, and the Storage Read API session may hand back fewer than
  requested (never more), so a per-stream row
  bound enforced at read time remains the real guard regardless of this split, and the exact row
  count costs one extra round trip beyond what `ExecuteQuery` needs. The patch reuses
  `job_query.go`'s existing `streamRecordBatches`/channel machinery for `ReadPartition` rather than
  building a second kind of stream reader, and needs no new Go module: the Storage Read API client
  was already a dependency of the default-stream read path. The patch adds `partitions_test.go`
  (descriptor round trip, malformed descriptor refused, dry run, empty query and bound parameters
  refused, the stream-count split function, both options' value refusals, the `CreateReadSession`
  and `ReadRows` requests as a fake Storage Read API on loopback receives them, and that a stream is
  closed when its schema fails to decode), which
  `nix/bigquery-adbc.nix`'s check phase runs by name on a host that can run its target; only the
  dispatch-only BigQuery venue sends them to real BigQuery, through `sutura-exec-bigquery`'s
  `split_leg` and `read_partition`. Upstream issue
  `adbc-drivers/bigquery#367`, upstream change
  [`adbc-drivers/bigquery#371`](https://github.com/adbc-drivers/bigquery/pull/371) (open, same
  behaviour on upstream's current source). Removal condition: the first `adbc-drivers/bigquery`
  driver release (`go/v*` tag) that contains #371; bump `bigquery-adbc-src` to it and delete the
  patch, its `nix/bigquery-adbc-drivers.nix` line and its check names. `telekom/sutura#1742`
  tracks that deletion.
