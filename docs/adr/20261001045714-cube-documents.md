# Cube documents

Status: **accepted** (per issue #1148 owner decisions, 2026-09-28).

## The question

A catalog defines many metrics. Some groups of metrics share a time column and a list of dimensions - each is the same fact table with a different measure. Authoring each as a separate metric document repeats the shared schema, inviting drift (a dimension declared on one but not another, or declared differently).

Should cubes be a first-class concept in the catalog, with their own schema? If so, should the domain see them as objects, or should they expand into metrics before reaching the domain? If a measure in a cube computes but is nonsensical (e.g., violates semantic constraints), should the whole cube refuse, or only that measure?

## Decisions

**Q1: Can a measure add dimensions beyond the cube's declared list?** No. A measure may only add constraints (filters), not structure. The type `MeasureDoc` under `CubeDoc` has no `dimensions:` field; `deny_unknown_fields` refuses it.

**Q2: How does the domain see a cube?** Only as expanded metrics. A cube is authoring sugar only. `CubeDoc::into_domain` expands each measure into an ordinary `Metric` at load time, inside `sutura-catalog-local`'s parser, before `Definitions::assemble`. The domain type `Metric` needs no new variant `Cube`, no newtype `CubeName`, and queries see no cube shape. The `<cube>_<measure>` naming convention is the only trace left.

**Q3: If a measure in a cube is invalid, what refuses?** Only that measure. One measure with an unknown Wren type, or a required filter on a column the model does not expose, refuses only itself. Its siblings and the cube still convert to metrics.

## Design

A `CubeDoc` in the file format declares:

- `name: MetricName` - the cube's name, joined with each measure's name to form the expanded metric name.
- `model: ModelName` - the table all measures read from.
- `time_column: ColumnName` - required; a cube with no time axis cannot be split by grain.
- `grains: [Grain, ...]` - the time buckets for all measures.
- `dimensions: [DimensionDoc, ...]` - optional; all measures see these.
- `measures: [MeasureDoc, ...]` - per-measure `measure`, `authored_sql`, `required_filters`, `anchor`, `audience`, and optional `description`.

Load-time expansion happens in `sutura_catalog_local`:

1. Parse the YAML into `CubeDoc`.
2. Validate: no empty measure list, no duplicate measure names, each measure's metric name is valid.
3. For each measure, construct a `MetricDoc` with the cube's `model`, `time_column`, `grains`, `dimensions`, plus the measure's own fields.
4. Convert each `MetricDoc` through the existing validator. It rejects invalid metrics as before; a single bad measure does not stop its siblings.
5. Return the vec of expanded metrics.

The expanded metrics are indistinguishable from hand-written ones. A cube document and its hand-flattened equivalent have the same digest because the canonical form is the expanded set of `Metric` values, not the cube document. Re-running a Wren import or hand-editing the source re-certifies the digest.

## Refusals

- **`InvalidCubeDocument::NoMeasures`**: Cube declares no `measures:`. Scope: the cube.
- **`InvalidCubeDocument::DuplicateMeasure`**: Two measures have the same `name`. Scope: the cube.
- **`InvalidCubeDocument::MetricName`**: Joining `<cube>_<measure>` does not parse as a metric name (too long). Scope: the cube.
- **`InvalidCubeDocument::Metric(m)`**: Expanded measure m fails as a metric document would. Scope: that measure only; siblings expand.
- **Denied by `deny_unknown_fields`**: Measure declares `dimensions:`, `model:`, `time_column:`, `grains:`, or `hierarchies:`. Scope: parse-time on the measure or cube.

## Non-goals

- **Hierarchies:** Not supported. The vocabulary has no domain-side hierarchy type, and `deny_unknown_fields` on `CubeDoc` refuses the key.
- **Per-measure dimension override:** Each measure inherits the cube's full dimension list. A measure needing different dimensions is a separate metric document.
- **Dotted addressing:** Measures are referred to as part of the `<cube>_<measure>` expanded name. No query syntax exists to say "the net_revenue measure of the subscription cube."
- **Per-measure audience narrowing beyond the metric:** ADR 0028 sets per-metric `audience:`; that is unchanged. Audience cannot be tightened at the measure level inside a cube.

## Future work: `shared_calendar:`

The issue #1148 owner noted that a measure reporting as a cross-model ratio (e.g., revenue over employee count) may need a different time calendar than the cube's, even though the cube defines one. A cube measure cannot yet declare `shared_calendar:` to link to another metric's grain. This will be supported in a later PR and recorded as an enhancement to this decision.
