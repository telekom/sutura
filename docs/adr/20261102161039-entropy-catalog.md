# Entropy catalog

Status: **accepted**, 2026-11-02 (issue #1729). These are the owner's decisions. Built so far: the
configuration (`catalog.kind: entropy`, its sign-in and its bindings) and the client credentials
grant it signs in with. **No build links the reader**, so every build refuses the kind by name at
boot.

## The question

An Entropy Data deployment holds data products whose output ports each name a data contract and a
server. sutura reads them as a catalog. Four things were open:

1. A contract's metric `formula` is free text, which nothing can compile. Where does a certified
   metric come from?
2. May an `entropy` catalog sit beside a catalog of another kind?
3. A port and its contract can each name a server. Which one is read?
4. Which specification versions are read?

## Decision

1. **Metrics come from a declared `metric_property`** in the contract's `customProperties`, as a
   `datahub` catalog's do. The parser that reads the property moves to a place both readers share.
2. **One catalog kind per deployment.** `open_catalog`'s refusal of mixed kinds stays.
3. **A port's server is read only when the port and the contract agree on it, or when only one of
   them names it.** A conflict is a typed load refusal naming the product and the port. A port's
   server has no `type` and free keys, so a server is matched by the fields a binding lists, below.
4. **ODCS v3.x and ODPS v1 are read.** The older DCS and DPS shapes are refused by name.

## Sign-in

A deployment declares exactly one mode. Both are the deployment's identity reading metadata: **no
caller's identity reaches the marketplace.** What a caller may read from a data system is decided by
that source's own posture, not by the catalog.

| Mode           | Sent as                                                                                | Reads                                                                                      |
| -------------- | -------------------------------------------------------------------------------------- | ------------------------------------------------------------------------------------------ |
| `api_key_file` | `Authorization: Bearer`, the key as the token                                          | whatever the key's owner - an organization, a team or a user - can see                     |
| `oidc`         | `Authorization: Bearer`, a token from the client credentials grant at `token_endpoint` | an agent client reads only the endpoints open to agents, products and contracts among them |

The marketplace takes an API key as `x-api-key`, as a bearer token or as a Basic password. Bearer is
chosen so both modes share one header, and a reader has no branch on the mode once it holds a token.
**No build sends either yet.**

The client authenticates at the token endpoint by HTTP Basic alone (`client_secret_basic`), the one
method the marketplace documents for agent clients and every authorization server must support. Each
grant is one request: nothing holds the token between calls.

`token_endpoint` is written, never derived from `endpoint`: the marketplace's authorization server is
on another host than its API.

What `oidc` does not cover:

- **An external issuer's `aud` is checked only when the marketplace registers that issuer with an
  audience.** sutura cannot see that registration, so it cannot refuse a deployment that lacks one.
- **`scope` is optional.** The marketplace's own authorization server lists only `mcp`, `mcp:read`
  and `mcp:write`, none for the REST API, and needs none. An external issuer may require one: it is
  sent as written and omitted when absent.
- **An issuer that needs an `audience` or `resource` parameter** is not served; only `scope` is
  sent.
- **The token endpoint and `scope` load unchecked.** The crate that sends them parses them, and no
  build links it yet.

## Bindings

A binding names one declared source for the servers its `match:` picks out: a server `type` and at
least one other field, every value a string.

```yaml
bindings:
  - match:
      type: postgres
      host: db.example.com
      port: 5432
    source: pg
  - match:
      type: bigquery
      project: example-project
      dataset: sales
    source: warehouse
```

A server matches when its type is the match's and every listed field equals the server's field of
that name rendered as text, an integer `port` as its decimal digits. Fields the match does not list
are ignored, so one shape reads every server type, including types sutura names nowhere else, and a
port's `server` object, whose type is the port's.

- **Exact string equality.** No case folding and no host normalization: `DB.example.com` is not
  `db.example.com`, and `postgresql` is not `postgres`.
- **Nothing checks that the source can serve the type.** A `bigquery` server bound to a `duckdb`
  source loads, and is read from it.
- **A match on the type alone is refused**: it would bind every server of that type to one source.
- **Two bindings that could match one server are refused at load**: the same type, and no field both
  list with different values. So no server a reader meets matches two bindings.
