# Cube documents

Status: **accepted** (issue #1148). Q1-Q3 are the owner's decisions of 2026-09-28, recorded at
`github.com/telekom/sutura/issues/1148#issuecomment-5868494177`. The `shared_calendar:` decision of
2026-10-01 is recorded at `github.com/telekom/sutura/issues/1148#issuecomment-5928058787`.

## The question

A catalog defines many metrics. Some groups of metrics share a model, a time column and a list of
dimensions - the same fact table with a different measure. Authoring each as its own metric document
repeats the shared schema and invites drift (a dimension declared on one but not another, or
declared differently).

Should a group like that have its own document shape? If so, does the domain see it as an object, or
does it expand into metrics before reaching the domain? And when one of its measures is bad, what
refuses?

## Decisions

**Q1: Can a measure add dimensions beyond the cube's declared list?** No. A measure adds constraints
(filters), not structure. `MeasureDoc` has no `dimensions:` field, and `deny_unknown_fields` refuses
the key.

**Q2: How does the domain see a cube?** Only as expanded metrics. `CubeDoc::into_domain` expands
each measure into an ordinary `Metric` at load time, inside `sutura-catalog-local`, before
`Definitions::assemble`. No domain type is added, and a query sees no cube shape. The grouping is
not recorded anywhere after load, and the name does not recover it: the `<cube>_<measure>` join is
not invertible, so cube `sales` with measure `net_revenue` and cube `sales_net` with measure
`revenue` both expand to `sales_net_revenue`. That collision fails the load as
`InconsistentDefinitions::DuplicateMetric` ("metric sales_net_revenue is declared twice"), which
names neither cube nor file.

**Q3: If a measure is bad, what refuses?** The owner's answer, "a bad Wren measure refuses only
itself", governs the Wren converter (#1148 PR 2, #1193), not this loader. In the local loader one
refused measure refuses its cube, and the loader stops at its first refusal, so the whole catalog
fails to load. Held by `a_measure_its_metric_refuses_refuses_the_cube_rather_than_vanishing`: a
mutation that skipped the refused measure and kept its siblings reddened it in review of #1191.

## Design

A `kind: cube` document declares:

- `name` - joined with each measure's `name` to form that measure's metric name.
- `model` - the model every measure reads.
- `time_column` - required; a cube without one is refused as ``missing field `time_column` ``.
- `grains` - the time buckets of every measure.
- `dimensions` - optional; every measure gets all of them.
- `measures` - a list; each entry has `name`, `measure` or `authored_sql`, `required_filters`,
  `anchor`, `audience` and an optional `description` (absent means the cube document's body).

`audience` exists only per measure and is required there; a cube has no audience of its own. Each
measure's audience becomes its metric's audience, which ADR 0028 makes the unit of visibility.

Expansion, in `CubeDoc::into_domain`:

1. Refuse a measure name declared twice, then an empty `measures:` list.
2. Per measure, join `<cube>_<measure>` into a metric name, and build a `MetricDoc` from the cube's
   `model`, `time_column`, `grains` and `dimensions` plus the measure's own fields.
3. Convert that `MetricDoc` with the same `into_domain` a metric document uses. The first refusal
   refuses the cube.

The expanded metrics then go through `Definitions::assemble` like any other. A cube document and
its hand-flattened equivalent pin the same digest, because the domain pins the expanded metrics
and never sees the cube (`a_cube_and_its_hand_flattened_equivalent_pin_the_same_digest`).

## Refusals

Each of these fails the whole catalog load.

- `measures: []`: `InvalidCubeDocument::NoMeasures` ("cube sales declares no measure").
- Two measures sharing a `name`: `InvalidCubeDocument::DuplicateMeasure`, naming the cube.
- A `<cube>_<measure>` join over the identifier length cap: `InvalidCubeDocument::MetricName`.
- A measure's metric refused as a metric document's would be: `InvalidCubeDocument::Metric`,
  carrying the metric document's own message.
- No `measures:` or no `time_column:` key: serde `missing field`, a frontmatter refusal.
- A measure declaring `dimensions:`, `model:`, `time_column:`, `grains:` or `shared_calendar:`, or a
  cube declaring `hierarchies:` or `shared_calendar:`: serde `unknown field`, by
  `deny_unknown_fields`.
- An expanded metric that does not hold together with the rest of the catalog (its name declared
  twice, a required filter on a column its model lacks, a term on an undeclared model):
  `InconsistentDefinitions`, naming the metric and neither the cube nor the file.

The four `InvalidCubeDocument` refusals arrive as `LocalCatalogError::Cube`, which names the file.

## Non-goals

- **Hierarchies:** the vocabulary has no roll-up order, and `CubeDoc` refuses the key.
- **Per-measure dimensions:** a measure needing a different dimension list is its own metric
  document.
- **Dotted addressing:** a measure is asked for by its expanded `<cube>_<measure>` name; no query
  syntax names "the `net_revenue` measure of the `subscriptions` cube".

## Decided, not yet built: `shared_calendar:`

`shared_calendar:` is how a cross-model (two-fact) ratio names the one conformed calendar model both
facts bucket through (ADR 0002, *Second amendment, 2026-09-28*). The owner decided on 2026-10-01 to
**support it**: a cube measure may be such a ratio declaring `shared_calendar:`, expands to the same
metric a hand-written document would declare, and is answered by the existing two-statement path.
An `anchor:` on such a measure stays refused at load (#780, #1194). It is built as its own PR after
#1193.

Limit until then: the key is refused by the parser as an `unknown field`, on a measure and on the
cube alike, so such a document does not load. That is held by `deny_unknown_fields` alone; no cell
pins it, and it was measured by a probe in review of #1191.
